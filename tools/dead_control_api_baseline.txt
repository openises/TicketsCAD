# --- SHAPE 1: extra structured fields alongside an already-consumed
#     human-readable string (the confirm()/message pattern) — the JS
#     shows data.message in a dialog/toast and never reads the
#     structured fields that would let it build a richer UI (a link to
#     the other unit, etc.). Verified: api/unit-assignments.php:209-215's
#     'message' field already embeds the same info
#     ("This member is currently assigned to <name>. Reassign?") that
#     current_unit_name/current_unit_id/current_assignment_id also
#     carry structurally; unit-detail.js's doAssignPersonnel confirm()
#     flow reads only .message. auto_bindings (same file, line 289/295)
#     is a count returned alongside 'success' that the caller doesn't
#     currently surface. Real API completeness, not a broken promise.
apikey:current_unit_name
apikey:current_unit_id
apikey:current_assignment_id
apikey:auto_bindings

# --- SHAPE 2: a permission flag returned by an endpoint, where the SAME
#     permission is ALSO delivered via a page-load global the JS
#     actually reads instead. Verified:
#     assets/js/org-relationships-admin.js:376 reads
#     window.ORR_CAN_ACT_GLOBAL / window.ORR_CAN_ACTIVATE, which
#     org-relationships-admin.php:351-353 sets directly from PHP at page
#     load — a completely separate channel from api/org-relationships.php's
#     own can_propose/can_activate_any list-response fields. The real
#     authorization check exists and is used; these two fields are a
#     redundant second copy of the same information. Not a security gap
#     (server-side RBAC still gates the actual write endpoints
#     independently either way) — a duplicate-plumbing cleanup
#     candidate, not urgent.
apikey:can_propose
apikey:can_activate_any

# --- SHAPE 3: a `caps`/permission-flag object returned so a future or

#     endpoint to refuse an unauthorized attempt (defense in depth still
