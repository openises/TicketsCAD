# UI-consistency audit baseline — tools/ui_consistency_audit.php
#
# One finding key per line. A key listed here is KNOWN, REVIEWED interface debt
# that the audit must not fail on; anything not listed fails the build. That
# split is the whole point: existing debt does not block work, NEW drift does.
#
# WHY THE AUDIT EXISTS (Eric, 2026-07-31)
# ---------------------------------------
# A newly shipped widget was reviewed on a live system and found inconsistent
# with every other widget in the product — action hotkeys as a run of text along
# the bottom instead of labelled keycap buttons in the header, a dismiss control
# with no way to reopen, and per-user state in a newly invented store while
# dashboard_layouts and user_screen_prefs already existed. In Eric's words: "I
# do not want the software to appear as if we have multiple developers who have
# never seen this software before or ever talked to each other, working on the
# same codebase."
#
# FORMAT
# ------
#     <rule-id>: <path> :: <whitespace-collapsed excerpt of the offending source>
#
# Line numbers are deliberately absent so an entry survives reformatting and
# code moving up or down a file. The excerpt is present so a SECOND, different
# violation in an already-baselined file is a NEW key and still fails — a
# per-file key would have let a file be waived once and drift forever.
#
# `php tools/ui_consistency_audit.php --rules` prints the convention behind
# every rule id. docs/UI-CONVENTIONS.md explains the reasoning, with the
# file:line evidence each rule was derived from.
#
# BEFORE ADDING A KEY HERE
# ------------------------
# Adding a line is declaring that this piece of interface is deliberately
# unlike the rest of the product. Almost always the cheaper answer is to follow
# the convention — these are not stylistic preferences, they are the reason the
# application looks like one application:
#
#   theme-color       a hardcoded hex is the same colour in dark mode. If the
#                     surface genuinely has no theme (print output), exclude it
#                     in the tool with a reason rather than baselining it.
#   control-size      dispatch forms are compact by design.
#   form-button-type  this one is a live bug, not a style point: a <button>
#                     with no type inside a <form> submits and reloads the page
#                     (GH #84). Fix it; do not baseline it.
#   state-store       per-user layout/column state saved only in the browser
#                     does not follow the dispatcher to another machine.
#
# A legitimate entry names a considered exception and says why, in a comment
# above it — as the schema, api-contract, legacy-level and clock baselines do.
#
# THE SNAPSHOT BELOW
# ------------------
# Generated 2026-08-01 against the tree as it stood, and it is a picture of real
# debt rather than a formality. The concentration is one rule: hardcoded colours
# that cannot follow the theme, mostly in the older per-page stylesheets
# (radio-widget, dashboard, config, callboard, mobile) written before the
# Bootstrap-variable convention settled. Several of them are literally the
# Bootstrap palette values typed out by hand (#0d6efd, #198754, #6c757d), which
# is the drift in its purest form.
#
# Two entries are worth pulling out, because they are defects rather than style:
#
#   form-button-type: unit-edit.php — btnAddSource and btnAssignPersonnelEdit
#   sit inside <form id="unitForm"> with no type=, so they submit the form and
#   reload the page. That is GH #84 again, in the same file GH #84 was reported
#   against ("the unit-edit OwnTracks button immediately refreshes the page").
#   They are baselined only because this session owns the audit and not that
#   file; they should be fixed, not waived.
#
#   state-store: aprs-map.php — the APRS page runs its own GridStack and saves
#   the tile layout and column config to localStorage alone, so an operator's
#   arrangement is stranded on one browser. The dashboard solves the same
#   problem through api/layout.php.

# ── widget-registry (1) ───────────────────────────────────────────────
# ACCEPTED. The Phase 131 check-in panel is a floating overlay, not a grid
# tile: it renders on the dashboard AND on situation.php, which has no
# GridStack at all. It carries a widgets-toolbar toggle so it has a re-open
# path — which is the point of the rule — but deliberately no DEFAULT_LAYOUT
# entry, icon, template or saved geometry, because it is not laid out by the
# grid. This is the "floating panel with a toolbar toggle" case the rule
# describes, and it is the right shape for it.
widget-registry: assets/js/widget-manager.js :: net_checkins registered outside DEFAULT_LAYOUT: .widget-toggle button (index.php)

# ── widget-header (1) ───────────────────────────────────────────────
# DEBT. aprs-map.php runs a second, private GridStack (two tiles, ~90 lines of
# page-local CSS re-implementing grid styling) instead of the dashboard's
# widget system, so its tile headers are hand-built and have no refresh
# control. Worth folding into the shared engine; too large for a passing fix.
widget-header: aprs-map.php :: <div class="card-header"

# ── hotkey-affordance (1) ───────────────────────────────────────────────
# ACCEPTED. A single <kbd>Esc</kbd> hint beside the navbar search field. One
# keycap labelling the field you are already in is a hint; the rule is about a
# run of them acting as an action legend for a panel, which is what belongs in
# the header as buttons.
hotkey-affordance: inc/navbar.php :: 1 <kbd> outside an action button

# ── state-store (2) ───────────────────────────────────────────────
# DEBT. Same root cause as the widget-header entry above: aprs-map.php's
# private GridStack persists its tile layout and column config to localStorage
# alone, so an operator's arrangement is stranded on one browser. The dashboard
# solves exactly this through api/layout.php -> dashboard_layouts.
state-store: aprs-map.php :: localStorage.setItem('aprsGridLayout')
state-store: aprs-map.php :: localStorage.setItem('aprsListColConfig')

# ── form-button-type (2) ───────────────────────────────────────────────
# NOT ACCEPTED — these are live defects, listed only because the session that
# added this audit did not own unit-edit.php. Both sit inside <form
# id="unitForm"> (unit-edit.php:104) with no type=, so clicking either submits
# the form and reloads the page instead of running its handler. That is GH #84
# again, in the very file GH #84 was reported against ("the unit-edit OwnTracks
# button immediately refreshes the page"). Fix them and delete these two lines.
